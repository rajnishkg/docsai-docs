# Resolve conflicts

A conflict happens when your branch and the published base changed the same lines, for example when someone edited the same paragraph on GitHub. The console resolves conflicts file by file, without Git commands.

<Steps>

<Step>

## Update the branch

On your branch, choose **Update from published base**. Without overlapping changes the console merges and answers *Branch updated from the published base*. With overlapping changes it answers that the update has conflicts in a number of files, *Resolve each file below; nothing was changed yet.*, and opens **Resolve conflicts with the published base**.

</Step>

<Step>

## Compare the versions

Each conflicted file shows three read-only versions side by side: **Base (common ancestor)**, **Yours (branch)** and **Published**, and below them an editable **Result for** the file.

</Step>

<Step>

## Choose the result

Choose **Take yours** or **Take published** to start from one side, then edit the result until it reads right. Conflict markers (`<<<<<<<`) are rejected.

</Step>

<Step>

## Commit the merge

Choose **Commit resolved merge**. The console answers *Merge committed* and the merge is a new commit on your branch: it needs a new review.

</Step>

</Steps>

If the branch is also open as a pull request, choose **Push & open PR** after the merge: the pull request gets the resolved commit.

## Avoid conflicts

- Keep branches short-lived and focused on one topic.
- Choose **Update from published base** before you start a long edit.
- Agree who edits a page when two people change it the same day. The console shows others active on the same file.
