# Publish an OpenAPI definition

Add an OpenAPI definition to the repository and list it in `catalog.json`. Each release then includes an API reference page with **Test Request**, built from the exact reviewed commit. This site publishes the [DocsAI console API](/docs/docsai/v1/console-api/) this way.

## Lay out the API bundle

Keep each API version in its own folder under `apis/<product>/<api-id>/<version>/`:

```text title="apis/docsai/console-api/v1/"
openapi.yaml            the whole definition: info, servers, tags, security, paths, components
content/overview.md     guides shown with the reference
content/authentication.md
content/errors.md
```

<Callout type="warning" title="Keep the definition in one file">

The reader builds the reference from `openapi.yaml` itself. When paths are split into separate files with `$ref: ./paths/….yaml`, the release validates, but the reference page says *This API declares no HTTP operations.* Keep paths and schemas in `openapi.yaml` and use `$ref` only inside it (`#/components/schemas/…`).

</Callout>

<Steps>

<Step>

## Write the definition

Use OpenAPI 3.1 (3.0 works too). Give every operation an `operationId`, a `summary`, a `description`, a tag and responses with an `example`: examples are what the mock server answers and what readers see.

```yaml title="apis/docsai/console-api/v1/openapi.yaml"
openapi: 3.1.0
info:
  title: DocsAI console API
  version: v1
paths:
  /api/projects:
    get:
      operationId: listProjects
      tags: [Projects]
      summary: List projects
```

</Step>

<Step>

## Add the catalog entry

Add the API to `apis` in `catalog.json`. `bundleFiles` lists the definition and `documentationFiles` the Markdown guides under `content/`.

```json title="catalog.json"
{
  "id": "console-api", "product": "docsai", "version": "v1", "slug": "console-api",
  "kind": "openapi", "title": "DocsAI console API",
  "file": "apis/docsai/console-api/v1/openapi.yaml",
  "bundleRoot": "apis/docsai/console-api/v1",
  "bundleFiles": ["apis/docsai/console-api/v1/openapi.yaml"],
  "documentationFiles": ["apis/docsai/console-api/v1/content/overview.md"],
  "classification": "public", "lifecycle": "published",
  "owner": "documentation-team", "reviewDate": "2027-11-13",
  "environments": [{"id": "mock", "label": "Local mock", "kind": "mock", "baseUrl": "http://127.0.0.1:4020", "enabled": true}]
}
```

</Step>

<Step>

## Commit, review and publish

Commit on a branch, submit, get approval and publish, like a page. The reference appears at `docs/<product>/<version>/<slug>/`, here `/docs/docsai/v1/console-api/`, under the **API reference** tab. It starts with an overview: the operations, the authentication schemes, the test servers, and links to download the definition and Postman and Bruno collections.

![The API overview of the DocsAI console API on the reader site](assets/docsai/v1/screenshots/publish-an-openapi-definition/01-reader-api-overview.png)

Below the overview, each tag and operation has its own section with parameters, responses, examples and a **Test Request** button.

![The Get the current session operation with its request sample and Test Request](assets/docsai/v1/screenshots/publish-an-openapi-definition/02-reader-operation-reference.png)

</Step>

</Steps>

<Callout type="info" title="Public or private">

Only an API with `"classification": "public"` and `"lifecycle": "published"` reaches readers. For an internal API use `"classification": "protected"`. See [Keep an API private](/docs/docsai/v1/private-apis/).

</Callout>
